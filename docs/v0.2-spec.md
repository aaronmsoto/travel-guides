# Juntar v0.2 — Collaboration platform specification

Status: **draft for host review** · Author: the v0.1 build team (Claude with Aaron) · Date: 2026-09-23
Applies to: https://juntar.net/ · Repo: `aaronmsoto/travel-guides` · Supersedes nothing; v0.1 stays live throughout.

Supporting research memos (cited throughout): `docs/research/auth-rsvp-privacy.md`,
`docs/research/backend-options.md`.

---

## 0. Summary for the host

v0.1 is a set of static trip invitations. It does the "showing off the destination and the plan" half of
the job well, and it stops exactly where a group forms: the reader copies a link to their picks and
sends it to you by chat, and you keep the roster in your head and in `guide.json`.

v0.2 closes that loop **without giving up what v0.1 got right**: the guides stay declarative, static,
fast and self-contained; a small set of *dynamic islands* (sign-in, RSVP, roster, host tools,
host announcements) talk to a hosted backend. Concretely, after v0.2:

- Anyone with the link can still read every guide, with no account. Public readers see **no personal
  information** — at most an aggregate ("8 people in so far · 3 vehicles"), and only if you allow it.
- A friend signs in with **first name + email** (phone optional as a contact; SMS sign-in is phased,
  see §6) via a six-digit one-time code. No passwords, no profiles beyond that.
- They RSVP per trip: **going / maybe / can't**, party size (adults and kids as *counts*), which nights,
  whether they're bringing a vehicle, a note to the host, and their existing "My picks".
- Everyone who has RSVP'd or marked themselves **interested** sees who else is in — **first names and
  party sizes only**, never contact info.
- **Hosts** see everything for **their own trips** only: full roster, contact info, notes, capacity,
  and a one-screen dashboard. Hosts can **enter RSVPs on behalf of people** who answered at school
  pickup or in a group chat; when that person later signs in with the same email or phone, the entry
  becomes theirs automatically.
- Transactional messages (codes, confirmations, changes, reminders) go out by email; **host announcements** to a trip's
  participants ship in the second increment. Conversation stays in the group's existing chat, which
  the research says is what every small event platform does.

The plan is split into three shippable increments (§11). The first one is scoped to be live before the
Zion trip's booking deadline; the third adds SMS once the US carrier registration that SMS now
requires is done. Open decisions for you are collected in §14.

## 1. Where v0.1 stands (analysis)

**What exists.** Three guides (`mecca-hills` potential Oct 24–25 2026; `zion` planning Nov 21–25
2026; `death-valley` planning Jan 15–18 2027) rendered by `tools/build.py` from `guides/<slug>/guide.json`
into self-contained HTML, deployed by GitHub Actions to GitHub Pages at juntar.net. Client JS is
~250 lines of vanilla code (`shared/engine.js`): hash routing, My picks in `localStorage`, a
"copy a link to my picks" share loop, countdown, units, theme, photos + map, packing checklist.

**What the response loop looks like today.**

| Step | v0.1 mechanism | Failure mode |
|---|---|---|
| Learn about the trip | Static guide, Trip tab first | Works; noindex, shared by link |
| Decide what to do | Top 10 → My picks (localStorage) | Picks are per-browser; lost on another device |
| Say "we're in" | Copy picks link → paste to host in chat | Off-site; nothing recorded; host transcribes |
| Know who else is in | `trip.roster[]` typed by host in `guide.json`, rebuilt, redeployed | Stale within hours; requires a commit and deploy for every change; shows names to the public |
| Capacity | `trip.capacity.peopleTaken` typed by host | Same |
| Questions | FAQ + "coordinate with the host" | Host answers the same question in several chats |
| Reminders | `trip.ics` download; key dates list | Nothing proactive |

**The v1 critique already flagged this.** `_reviews/critique-product.md` scored the share/response loop
as the weakest area of the product: readers can't commit on the page, the host can't see commitments,
and the roster is both public and stale. The host's own decision log (`CLAUDE.md`, 2026-09-17)
deferred RSVP mechanics to "coordinate with the host" precisely because a static site can't hold
personal data safely. v0.2 is the deliberate answer to that deferral.

**What must not change.** The declarative content pipeline (JSON → validate → build → deploy), the
research-with-sources discipline, the image licensing rules, the no-day-by-day-schedule stance, the
"drivers from LA/OC" framing, and the family-photo rules all stay. Anything in v0.2 that would require
hand-editing built HTML or mixing personal data into the repo is out.

## 2. Vision and principles

**Vision.** *Juntar* ("to bring together") is the place where a small circle of friends and school
families says yes to the same weekend. The guide shows them why; v0.2 lets them say "we're in" on the
page, shows them who else is coming, and gives the host one screen instead of five chat threads.

**Principles** (each one is a test we apply to every feature below):

1. **Content stays declarative and static.** Guides remain `guide.json` → build → static HTML. Dynamic
   behavior lives in islands that degrade gracefully: if the backend is down, the guide still reads
   exactly like v0.1.
2. **Privacy by default, enforced on the server.** Unauthenticated readers never receive personal data,
   not because the client hides it but because the API can't return it. Visibility rules are declared
   as database policies and tested in CI.
3. **Ask for the minimum.** First name plus one contact channel is a complete account. Everything else
   (phone as a second channel, dietary notes, vehicle) is per-trip and optional.
4. **Host-first, host-scoped.** The host coordinates; the site removes bookkeeping, not conversation.
   A host sees everything about their own trips and nothing about other hosts' trips.
5. **Off-platform answers count.** A "yes" said at pickup is as real as a click; hosts can record it,
   and the person can claim it later.
6. **Adults only, kids as counts.** Accounts are for adults; children appear as numbers in a party,
   never as profiles or names.
7. **Declarative operations.** Schema, policies, email templates, and environment config live in the
   repo and are applied by CI. An AI coding agent can operate the whole system from the repo.
8. **Low cost, low lock-in.** Hobby budget; Postgres-standard data; export is one command.

## 4. Scope

**In scope for v0.2** (all increments): passwordless sign-in (email OTP first; SMS OTP phased);
minimal profile; per-trip RSVP with party size, nights, vehicle, note, picks; interested state;
visibility rules by role; host dashboard scoped to own trips; host proxy RSVPs with claim-on-sign-in;
member approval for unknown sign-ups; transactional email (and later SMS); per-trip host announcements (no
threads or direct messages); reminders; user data export and deletion; privacy notice; audit log.

**Explicitly out of scope for v0.2** (candidates for v0.3): self-serve trip creation in the browser
(trips are still declared in `guide.json` and registered by CI); direct messages between members;
member photo uploads; date polls; payments or cost splitting; public discovery or search indexing;
multi-language UI; native apps; push notifications.

## 5. User stories and acceptance criteria

Stories are numbered for traceability; increments in §11 reference them.

### Sign-in and profile (A)
- **A1** As an adult with the link, I can sign in with my first name and email by typing a six-digit
  code sent to that email, in under 60 seconds, on a phone. *AC:* code valid 10 minutes, single use,
  5 attempts; same-device and cross-device (read on laptop, type on phone) both work.
- **A2** I can add a mobile number to my profile as a second contact channel and verify it with a code.
  *AC:* phone is optional; stored E.164; used for claim-matching (D2) and, when enabled, notifications.
- **A3** I stay signed in on my device for 30 days; I can sign out everywhere. *AC:* session revocation
  takes effect within one minute.
- **A4** My profile holds only first name, optional last initial, email, optional phone, and notification
  preferences. *AC:* no other fields exist in the schema.
- **A5** If I'm not yet known to any host, my account is *pending*; I can read guides and RSVP, but my RSVP
  and the roster are visible only after a host approves me (§7.3). *AC:* pending users receive an
  explanation; hosts get a notification with approve/decline.

### RSVP (B)
- **B1** On a trip page, signed in, I can set going / maybe / can't and change it any time before the trip
  ends. *AC:* one RSVP per person per trip; history kept in the audit log. A **waitlist** status exists
  for trips with a real capacity (the host moves people between going and waitlist; §10.2).
- **B2** I can state my party: adults count, kids count, which nights (from the trip's date range), whether
  I'm bringing a vehicle (and what), and a note to the host. *AC:* nights default to all trip nights;
  vehicle description ≤ 80 chars; note ≤ 500 chars.
- **B3** My picks (Top 10 tiles) attach to my RSVP so the host sees "what we might do" preferences. *AC:*
  picks sync from `localStorage` on first sign-in; the existing copy-a-link flow keeps working for
  anyone not signed in.
- **B4** I can mark a trip **interested** without a party; that makes me a follower (I see the roster
  and announcements; I’m not counted). *AC:* interested shows in the host dashboard as a separate list.
- **B5** I receive an email confirming my RSVP and any change, with the trip's key dates and an ICS
  attachment. *AC:* one email per change, sent within a minute.

### Seeing who's in (C)
- **C1** As a public reader I see the trip's aggregate only when the host allows it: "N people in · M
  vehicles" — no names. *AC:* the anonymous API returns counts only; every other endpoint returns 401.
- **C2** As an RSVP'd or interested member, I see the roster for that trip: first name (+ last initial when
  two first names collide), status, party size, nights, vehicle yes/no. No email, phone, or notes.
  *AC:* a policy test proves contact columns are unreadable by non-hosts.
- **C3** Host-entered (proxy) entries look like everyone else's in the roster, with a small "added by
  host" marker. *AC:* claimed entries lose the marker.

### Host tools (D)
- **D1** As a host I see a dashboard per trip I host: counts vs capacity (people, vehicles, per night),
  going/maybe/can't/interested lists with contact info and notes, picks tally, pending approvals.
  *AC:* a host of Zion cannot read any Death Valley RSVP (policy test).
- **D2** I can add an RSVP for someone who answered off-platform: first name, status, party, nights, and
  optionally their email or phone. If that email/phone later signs in, the entry becomes theirs; if
  it can't be matched, I can merge it manually. *AC:* claim happens at first sign-in, is idempotent,
  and is logged.
- **D3** I can invite people by entering first name + email/phone; they arrive pre-approved and can be
  emailed the link. *AC:* invitation emails are opt-in per invitee and rate-limited.
- **D4** I can set capacity (people, vehicles), the RSVP deadline, and whether public counts are shown;
  I can close RSVPs. *AC:* these are per-trip settings in the database, not in `guide.json`.
- **D5** I can export my trip's roster as CSV. *AC:* includes contact info; logged.

### Communication (E)
- **E1** As a host I can post an announcement to a trip; members going/maybe/interested get it by email
  (and later SMS) unless they've opted out. *AC:* one send per announcement; unsubscribe link.
- **E2** As a participant I can see past announcements on the trip page and a link to the group's
  existing chat (set by the host, shown only to participants). *AC:* no threads, replies, or direct
  messages in v0.2 (see §10.1 for why); the chat link is never in the static HTML.
- **E3** Members get reminders at the trip's key dates (booking deadline, T-7, T-1) with the ICS. *AC:*
  reminders are derived from `trip.keyDates` and `trip.start`; each is sent once.

### Data rights and operations (F)
- **F1** I can download everything Juntar holds about me and delete my account; deletion anonymizes my
  RSVPs (keeps counts) and removes contact info. *AC:* self-serve; completes immediately.
- **F2** A privacy notice states what is collected, why, who sees it, retention, and how to delete.
- **F3** Every read of contact info by a host and every proxy/claim/merge is in an audit log the admin
  can inspect.
- **F4** Schema, policies, functions, and templates are applied from the repo by CI; a fresh environment
  can be created from the repo alone.

## 6. Authentication

Research basis: `docs/research/auth-rsvp-privacy.md` §1. Decisions:

### 6.1 Factor: six-digit email code, not a magic link, not SMS (at first)

- **Email one-time code is the login factor for every account.** Codes are six digits, valid 10
  minutes, single use, hashed at rest, 5 wrong attempts before a new code is required.
- **Why not magic links:** school-district and corporate mail gateways (Defender Safe Links, Mimecast,
  Proofpoint) pre-fetch links and burn single-use tokens, which produces "link expired" for exactly
  this audience. Codes also work across devices (read on the laptop, type on the phone).
- **Why not SMS at launch:** US carriers now require A2P 10DLC or toll-free registration for any
  application SMS, which costs setup fees, a monthly campaign fee, and one to four weeks of approval;
  SMS pumping fraud targets public phone-OTP forms; and NIST SP 800-63B-4 classifies SMS OTP as a
  *restricted* authenticator. None of that is worth it for tens of users when email reaches them.
- **Phone in v0.2.0 is a contact field**, entered optionally, stored in E.164, unverified. It is used
  to *suggest* proxy-RSVP matches to the host (§8.4), never to auto-claim, because an unverified
  number could be typed by anyone.
- **SMS sign-in and SMS notifications are increment v0.2.2** (§11), switched on only after the host
  approves the recurring cost and the carrier registration is done. Supabase Auth supports phone OTP
  through the host's own Twilio Verify account, so this is configuration, not architecture.
- **Passkeys** are deferred; revisit if sign-in friction is a real complaint.

### 6.2 Sessions

- Supabase Auth issues a short-lived access token (JWT, one hour) and a refresh token; the client
  library keeps them in `localStorage` and refreshes silently. Requests carry a bearer header, so
  there is no cross-domain cookie, no `SameSite` negotiation, and no CSRF surface for state changes.
- Refresh-token lifetime is set to **30 days of inactivity** ("stay signed in on this device").
- "Sign out everywhere" calls the global sign-out, which revokes every refresh token for the user.
- The trade-off of bearer tokens is XSS: a script on the page can read the token. Mitigation is the
  discipline v0.1 already has (no third-party JS except SRI-pinned Leaflet) plus a
  `Content-Security-Policy` meta tag emitted by `build.py` (§9.3).

### 6.3 Account creation and identity

- First sign-in with a new email creates the auth user; a database trigger creates the profile from
  the first name typed on the sign-in form. No separate "register" step.
- Email is normalized (`lower(trim(email))`); phone to E.164. Both are unique across profiles.
- Changing email or phone re-verifies the new value (email by code now; phone by code once SMS
  exists, otherwise it stays marked unverified).

### 6.4 Rate limits and abuse controls (all server-side)

| Control | Limit |
|---|---|
| Code requests per email | 5 per hour, 60-second cooldown between sends |
| Code requests per IP | 20 per hour |
| Wrong code attempts | 5 per code, then a new code is required |
| Response to unknown vs. known email | identical wording and timing (no enumeration) |
| Sign-in form | Cloudflare Turnstile or hCaptcha only if abuse appears; not at launch |

Supabase Auth enforces the per-email and attempt caps natively; the per-IP limit is the platform's
default and is left on.

### 6.5 What the user sees

1. On a trip page: "Sign in to RSVP" → first name + email fields (phone optional, labeled "so the
   host can reach you; we won't text you").
2. "Enter the 6-digit code we emailed" with a resend link that appears after 60 seconds.
3. Signed in: the RSVP card replaces the "Want to come?" text; the roster card appears if the
   person is a participant and an approved member (§7.3).

## 7. Visibility and authorization model

### 7.1 Roles

Roles are **per trip**, not global, except *admin*:

- **anonymous** — no session.
- **member** — signed-in, approved account (§7.3).
- **pending** — signed-in, not yet approved by any host.
- **participant(trip)** — member with an RSVP (going/maybe/can't/waitlist) or *interested* on that trip.
- **host(trip)** — listed in `event_hosts` for that trip. A member can host one trip and merely
  participate in another.
- **admin** — the site operator; can approve members, manage hosts, and read the audit log. Admin does
  **not** implicitly see other hosts' contact data in the UI; the database policy grants admin the same
  rights as a host on every trip, and every such read is audited.

### 7.2 Visibility matrix

| Data | anonymous | pending | member (not on trip) | participant(trip) | host(trip) | host(other trip) | admin |
|---|---|---|---|---|---|---|---|
| Guide content, trip dates, status | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| Aggregate counts (people, vehicles) | host setting | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| Own RSVP and profile | — | own | own | own | own | own | own |
| Roster: first names, status, party, nights, vehicle y/n | — | — | — | ✓ | ✓ | — | ✓ |
| Contact info (email, phone) of others | — | — | — | — | ✓ (this trip's participants) | — | ✓ (audited) |
| Notes to host, picks of others | — | — | — | — | ✓ | — | ✓ |
| Proxy RSVP source (who entered it) | — | — | — | marker only | ✓ | — | ✓ |
| Announcements, group-chat link | — | — | — | ✓ | ✓ | — | ✓ |
| Pending approvals, invitations | — | — | — | — | ✓ | — | ✓ |
| Audit log | — | — | — | — | own actions | — | ✓ |

Rules of thumb: the row for **anonymous** is entirely non-personal; the **host(other trip)** column is
identical to **member (not on trip)**; **participant** never sees a contact column.

### 7.3 Membership gate

The site is shared by link and is `noindex`, but links travel. To keep strangers out of rosters without
adding join codes to every trip:

- People a host **invites** or **proxy-enters** with an email are pre-approved: their first sign-in
  matches on the normalized email and lands as *member* (a phone match only suggests a merge to the
  host until phones can be verified, §8.4).
- Anyone else who signs in is *pending*: they can read, and they can submit an RSVP, but the roster and
  announcements stay hidden and their RSVP is shown to the host under "needs approval". Any host can approve
  (this promotes them to member site-wide; hosts of other trips still don't see their data).
- Blocked accounts can sign in but see nothing beyond the public site.

This is the "approval required" pattern that small-event tools use for link-shared events, adapted so
that the common case (a friend the host already told about the trip) has zero friction.

## 8. Data model

Research basis: `docs/research/backend-options.md` §4, refined for the visibility matrix in §7.2.
Postgres on Supabase; every table has row-level security (RLS) enabled; the browser only ever uses
the public *anon* key, so RLS and the security-definer functions below are the entire authorization
surface. Full DDL lands in `supabase/migrations/` (§9.5); this section is the contract.

### 8.1 Tables

| Table | Purpose | Key columns |
|---|---|---|
| `profiles` | One row per adult account (mirrors `auth.users`) | `id`, `first_name`, `last_initial?`, `email_norm` (unique), `phone_norm?` (unique), `phone_verified` bool, `member_status` (`pending` \| `active` \| `blocked`), `is_admin` bool (set only by SQL), `notify_email` bool, `notify_sms` bool, `created_at` |
| `events` | One row per trip; **`slug` equals `guides/<slug>`** | `id`, `slug` (unique), `title`, `status` (`potential` \| `planning` \| `confirmed`), `start_date`, `end_date`, `capacity_people?`, `capacity_vehicles?`, `rsvp_deadline?`, `rsvps_open` bool, `show_public_counts` bool, `chat_url?`, `created_at` |
| `event_hosts` | Who hosts which trip | `event_id`, `user_id`, `role` (`host` \| `cohost`) |
| `invitations` | People a host has invited by contact, pre-approving them | `id`, `event_id?` (null = site-wide), `invited_by`, `first_name`, `email_norm?`, `phone_norm?`, `sent_at?`, `accepted_by?`, `created_at` |
| `rsvps` | One per person per trip, real or proxy | `id`, `event_id`, `user_id?` (null until claimed), `status` (`going` \| `maybe` \| `cant` \| `interested` \| `waitlist`), `adults` int, `kids` int, `nights` date[], `vehicle` bool, `vehicle_desc?`, `picks` text[], `note?`, `is_proxy` bool, `proxy_first_name?`, `proxy_email_norm?`, `proxy_phone_norm?`, `entered_by?`, `claimed_at?`, `created_at`, `updated_at`; unique `(event_id, user_id)` where `user_id` is not null |
| `announcements` | Host broadcasts per trip | `id`, `event_id`, `author_id`, `body`, `sent_at?`, `created_at` |
| `notifications` | Outbox for every email (later SMS) | `id`, `user_id`, `event_id?`, `channel`, `kind` (`otp` is *not* here; Auth sends those), `dedupe_key` (unique), `payload` jsonb, `status` (`queued` \| `sent` \| `failed`), `created_at`, `sent_at?` |
| `audit_log` | Append-only record of sensitive actions | `id`, `actor_id?`, `event_id?`, `action`, `target` jsonb, `created_at` |
| `heartbeat` | One row a weekly job updates to keep the free project active (§13) | `id`, `touched_at` |

Kids are **counts** (`rsvps.kids`); there is no table where a child could appear. Nights are the subset
of the trip's nights the party is present, defaulting to all of them. `picks` holds attraction ids from
the guide (the same ids `engine.js` keeps in `localStorage` today).

### 8.2 Row-level security (summary of the policies)

| Table | anon | authenticated user | host of that event | admin |
|---|---|---|---|---|
| `events` | select | select | update settings columns | all |
| `profiles` | — | select/update own row (not `is_admin`, `member_status`) | select rows of that event's participants (audited) | all |
| `event_hosts` | — | select own rows | select for own events | all |
| `invitations` | — | — | all for own events | all |
| `rsvps` | — | select/insert/update own row (`is_proxy`, `entered_by` forced false/null) | all rows of own events | all |
| `announcements` | — | select for events where the user is an active participant | insert/select own events | all |
| `notifications` | — | select own | — | all |
| `audit_log` | — | — | select own actions | select |

Participants never get a direct `select` on other people's `rsvps` rows. The roster they see comes from
a **security-definer function** that returns only the allowed columns:

- `event_roster(event_id)` → `display_name`, `status`, `adults`, `kids`, `nights`, `vehicle`,
  `is_proxy`, plus `email`, `phone`, `note`, `picks`, `vehicle_desc` **only when the caller hosts that
  event** (otherwise null). The function returns nothing unless the caller is an active member with an
  RSVP or *interested* row on that event, or a host of it, or admin. Every call by a host or admin
  that returns contact columns writes an `audit_log` row.
- `event_public_counts(event_id)` → people going, vehicles, maybe count; callable by anon; returns
  nothing when `show_public_counts` is false.
- `host_dashboard(event_id)` → counts vs capacity per night, lists by status, pending approvals,
  picks tally; hosts and admin only.

These policies are tested in CI with pgTAP (§9.5): the tests are the executable form of the matrix in
§7.2, including the negative cases (a Zion host reads zero Death Valley rows; anon reads zero
`profiles`; a participant's roster call has null contact columns).

### 8.3 Membership and hosts

- `member_status` starts as `pending` unless the first sign-in matches an `invitations` row or a
  proxy RSVP by normalized email, in which case the trigger sets `active` and records the match.
- Any host can approve a pending member (sets `active`); admin can block.
- Hosts are rows in `event_hosts`; admin adds them. The host of a trip is displayed from
  `guide.json → trip.host` in the static page (unchanged) and from `event_hosts` in the dashboard.

### 8.4 Proxy RSVP and claim flow

1. Host opens the dashboard for a trip → "Add someone who told you in person": first name, status,
   adults, kids, nights, vehicle, optional email or phone, optional note. Saved as an `rsvps` row with
   `is_proxy = true`, `user_id = null`, `entered_by = host`.
2. In the roster it renders as everyone else does, with a small "added by host" marker.
3. **Claim by email (automatic).** When any account signs in and its `email_norm` matches
   `proxy_email_norm` on a proxy row, the trigger sets `user_id`, `claimed_at`, marks the member
   `active`, and logs `rsvp.claim`. If the person already had their own RSVP on that trip, the proxy row
   is merged into it (their own status wins; the host is notified of the merge).
4. **Phone matches are suggestions, not claims.** An unverified phone match shows the host a "looks
   like the same person: merge?" prompt in the dashboard; merge is a host action and is logged. Once
   SMS verification exists (v0.2.2), verified-phone matches claim automatically like email.
5. **Manual merge.** The host can merge any proxy row into any participant on the same trip (for
   people who signed in with a different email). Logged; reversible for 30 days via the audit log.
6. Claim is idempotent: a proxy row can be claimed once; a second sign-in changes nothing.

## 9. Architecture

Research basis: `docs/research/backend-options.md` §§1–3. The recommendation there, adopted here, is
**GitHub Pages (unchanged) + Supabase (Postgres, Auth, RLS, Edge Functions, pg_cron) + Resend for
email**, with Twilio Verify added in v0.2.2 if SMS is approved.

### 9.1 Why this and not the alternatives

- **Supabase** because authorization is declared as SQL policies that live in the repo, are
  reviewable in a diff, and are testable locally: the same discipline the project already applies to
  `guide.json` and `tools/schema.md`. Email OTP is built in and free. The data is plain Postgres, so
  leaving is one `pg_dump`. Free tier covers this scale by orders of magnitude.
- **Not Firebase**: the roster and visibility rules are relational; Firestore rules express them
  awkwardly. **Not PocketBase**: no free host remains and the maintainer becomes the operator.
  **Not a hand-rolled Worker API**: viable and cheaper in the limit, but every visibility rule becomes
  hand-written code, which is the riskiest thing to get wrong here. **Not a framework migration**
  (Astro, SvelteKit, Next): it adds a toolchain and solves problems this site doesn't have.
- **Resend** for email because its free tier (3,000 emails per month) covers notifications with room
  to spare, it supports SPF, DKIM and DMARC on the free tier, and it acts as custom SMTP for
  Supabase Auth's code emails, which is required to escape Supabase's very low built-in mail limit.

### 9.2 Components

```
juntar.net (GitHub Pages, static, unchanged pipeline)
  guides/<slug>/index.html  ← build.py  ← guide.json + site.json
      └─ trip tab: "island" mounts here (shared/island.js, inlined by build.py)
             │  HTTPS, bearer token, cache: no-store
             ▼
<project>.supabase.co
  Auth (email OTP; phone OTP later)      Postgres + RLS + security-definer functions
  Edge Function: send-notifications      pg_cron: drain outbox, reminders, digests, heartbeat
             │
             ▼
  Resend (transactional email, juntar.net domain)   [v0.2.2: Twilio Verify for SMS]
```

The island is loaded from the page's own inlined script; `supabase-js` is fetched lazily from
jsDelivr with an SRI hash **only when the reader taps Sign in or RSVP**, so the guide stays
dependency-free until someone acts, exactly as Leaflet is loaded only when the map opens.

### 9.3 Changes to the static pipeline

- `site.json` gains `api: { "url": "https://<ref>.supabase.co", "anonKey": "…" }`. The anon key is a
  public key by design (RLS is the boundary). `build.py` emits it as `<script id="apicfg">` JSON.
- `build.py` emits a `Content-Security-Policy` meta tag: `default-src 'self'`, script from `'self'`
  plus the two pinned CDNs, `connect-src` limited to the Supabase project host, images from `'self'`
  and the OSM tile hosts. GitHub Pages cannot set headers, so the meta tag is the available form.
- `build.py` renders the Trip tab's "Want to come?" card with static fallback text and a mount point;
  the island replaces it when the API answers. If the API is unreachable, the page reads exactly like
  v0.1 plus one line: "Can't reach the guest list right now. Text the host."
- `tools/schema.md` **retires `trip.roster` and `capacity.peopleTaken` / `vehiclesTaken`** (validator
  warns if present); the live roster and counts come from the database. `trip.capacity.people` /
  `vehicles` / `note` stay in `guide.json` as the declared limits and seed the event row.
- New `tools/sync_events.py`: reads `slug`, `title`, `status`, `start`, `end`, `capacity` from every
  `guide.json` and upserts `events` (service key, run from CI on `main` and by the `publish` skill).
  `guide.json` remains authoritative for *what the trip is*; the database is authoritative for *who is
  coming and the host's live settings*.
- `engine.js` gains: picks sync to the RSVP on sign-in; the existing copy-a-link flow is unchanged for
  anyone who does not sign in.
- New static page `privacy/` rendered from `shared/privacy.md` (story F2).

### 9.4 The island (client)

One file, `shared/island.js`, vanilla JS in the style of `engine.js`, ~400 lines budget:

- state machine: `anon → code-sent → signed-in(pending|active) → participant`; hash routes
  `#trip/rsvp`, `#trip/roster`, `#trip/host` added to the existing router.
- views: sign-in card, RSVP card (status, adults, kids, nights checkboxes, vehicle, note, picks
  summary), roster card, announcements card, host dashboard (counts vs capacity, lists, add-person
  form, approvals, merge prompts, CSV export, settings).
- all reads use the functions in §8.2; all writes go through RLS-protected tables; no personal data is
  ever written into the static HTML or the page cache.
- accessibility parity with v0.1: live regions, focus management, reduced motion, 390 px layout.

### 9.5 Repository layout, environments, CI

```
supabase/
  config.toml            # auth settings (OTP length/expiry, refresh lifetime, SMTP), local ports
  migrations/*.sql       # schema, RLS, functions, cron jobs — the authorization contract
  tests/*.sql            # pgTAP tests of the visibility matrix (§7.2)
  functions/send-notifications/   # Edge Function: drains the outbox through Resend
  templates/*.html       # auth code email + notification templates
shared/island.js, shared/privacy.md
tools/sync_events.py
.github/workflows/
  pages.yml              # unchanged, plus: run sync_events.py after deploy (main only)
  supabase.yml           # PRs: supabase start + db reset + test db; main: supabase db push, deploy functions
  heartbeat.yml          # weekly: touch heartbeat row (free-tier pause guard) + smoke check
```

- **Local dev:** `supabase start` gives Postgres, Auth, and a local mail catcher (Inbucket) in Docker;
  an agent can run the whole OTP flow offline. `supabase db reset` applies migrations and seeds.
- **Migrations are the only way the schema changes.** `supabase migration new <name>`, edit, commit.
  CI refuses drift (`supabase db diff` must be empty).
- **Secrets:** `SUPABASE_ACCESS_TOKEN`, `SUPABASE_DB_PASSWORD`, `SUPABASE_SERVICE_ROLE_KEY`,
  `RESEND_API_KEY` as GitHub Actions secrets; never in the repo; the browser sees only the anon key.
- **Backups:** the weekly workflow also runs `supabase db dump` and stores it as an encrypted
  workflow artifact (90-day retention) until the host opts into Pro's managed backups.

## 10. Messaging and notifications

### 10.1 What "messaging" means in v0.2

Research (`auth-rsvp-privacy.md` §2) found that no small event platform ships threads or direct
messages as a core feature: Partiful, Meetup, Gathio and Mobilizon all do **host broadcast plus light
responses** and route conversation to the group's existing chat. The v0.1 host decision ("joining is
coordinated with the host in person/chat") points the same way. So v0.2 messaging is:

1. **Transactional** (v0.2.0): sign-in code; RSVP confirmation and change receipts (to the person, with
   ICS); "someone RSVP'd / needs approval" digests to the host; claim and merge notices.
2. **Host announcements** (v0.2.1): a host writes one message to a trip; it is stored, shown on the trip
   page to participants, and emailed to going/maybe/interested members who have not opted out.
   `Reply-To` is a no-reply address; the email and the page carry the trip's group-chat link
   (`events.chat_url`, participants only) for replies.
3. **Reminders** (v0.2.1): generated from `trip.keyDates` and `trip.start` (booking deadlines, T-7, T-1)
   to going/maybe members; each sent once (`dedupe_key`).
4. Not in v0.2: replies, reactions, threads, direct messages, member-to-member contact reveal.

### 10.2 Capacity and waitlist

Death Valley already declares a real limit (12 people, 3 vehicles at E1). When a host sets
`capacity_people` or `capacity_vehicles`, the dashboard shows the meter per night, and a "going" RSVP
that would exceed capacity is saved as `waitlist` with an explanation; the host promotes people
manually (no auto-promotion in v0.2, so the host stays in control of who sleeps where). Capacity is
advisory for trips without a limit set.

### 10.3 Delivery and preferences

- All sends go through the `notifications` outbox; pg_cron drains it every minute via the Edge
  Function; failures retry three times then mark `failed` with the provider error.
- Email from `hello@juntar.net` with SPF, DKIM and DMARC configured on the domain; plain-text part
  always included; transactional mail carries no unsubscribe link (CAN-SPAM exempt) but announcements
  and reminders carry a one-click preference link anyway.
- Preferences: `notify_email` (announcements and reminders; receipts always sent), `notify_sms` (v0.2.2,
  default off, explicit opt-in with STOP handling).
- Host notifications are batched into at most one email per hour per trip.

## 12. Security, abuse and privacy engineering

- **Authorization is server-side only.** RLS plus security-definer functions; the client never filters
  personal data. CI fails if any table lacks RLS or any new function lacks a test.
- **Least data.** Profile is first name, optional last initial, email, optional phone, two preference
  flags. No birthdays, no addresses, no child names. Kids are integers.
- **Contact info exposure is logged.** Every host or admin call that returns email or phone writes an
  audit row; the admin can review who looked at what.
- **Tokens.** Bearer tokens in `localStorage`, one-hour access tokens, 30-day refresh, global sign-out.
  CSP meta tag; no inline third-party scripts; SRI on both CDN scripts.
- **OTP abuse.** Limits in §6.4; identical responses for known and unknown emails; sign-in attempts
  logged; Turnstile added only if abuse appears.
- **SMS pumping (v0.2.2).** Twilio Verify Fraud Guard on; US numbers only; per-number and per-IP caps.
- **Injection and content.** Announcement and note bodies are plain text, rendered escaped (the `H()`
  allow-list in `build.py` is for authored guide content, not user input).
- **Secrets.** Only the anon key is public; service-role key and provider keys live in GitHub Actions
  secrets and Supabase function secrets.
- **Deletion and export.** Self-serve; deletion anonymizes RSVPs (keeps counts and nights, drops
  name, contact, note, picks) so hosts' capacity math survives.
- **Legal posture** (research §3): CCPA/CPRA thresholds are far above this site; COPPA is avoided by
  adults-only accounts and kids-as-counts; OTP email is transactional (no unsubscribe required);
  SMS, when added, is transactional-only templates with STOP handling. A plain-language privacy notice
  ships in v0.2.0.
- **Photos.** Unchanged from v0.1 (opt-in by upload, `private: true` to withdraw); v0.2 adds nothing
  that attaches names to photos.

## 13. Risks and mitigations

| Risk | Likelihood | Mitigation |
|---|---|---|
| Supabase free project pauses after 7 idle days (weeks can pass between trips) | High without action | Weekly `heartbeat.yml` writes a row and smoke-tests sign-in; if a pause still occurs, upgrade to Pro ($25/mo) — the only line item that could move the cost off $0 |
| Email codes land in spam for some parents | Medium | Custom domain with SPF, DKIM, DMARC; plain-text part; short subject; "check spam" hint after 30 s; resend |
| Forwarded links bring strangers to rosters | Low–medium | Membership gate (§7.3): unknown sign-ins are pending until a host approves; noindex stays |
| Proxy claim mismatches (person signs in with a different email) | Medium | Host merge prompt; phone-match suggestions; audit trail with 30-day reversal |
| Free-tier email limits during a burst (e.g., a reminder to 60 people) | Low | Resend allows 100/day free; outbox paces sends; Resend's first paid tier is $20/mo if ever needed |
| RLS mistake exposes contact info | Low but severe | pgTAP negative tests in CI; every policy change reviewed against §7.2; contact columns only via one function |
| Scope creep into a full social app | Medium | §4 out-of-scope list; v0.3 candidates parked; the host decides |
| SMS carrier registration delays or rejects a sole-proprietor brand | Medium (v0.2.2 only) | Toll-free verification as the fallback path; phone stays a contact field meanwhile |
| Host dashboard becomes the only place the host looks, and `guide.json` drifts | Medium | `sync_events.py` in CI keeps events aligned with guides; dashboard shows the guide's declared capacity next to the live setting |

**Cost summary** (from `backend-options.md` §3): email-only v0.2.0/v0.2.1 is **$0/month** at 100 or
500 users; SMS adds roughly **$6–14/month**; Supabase Pro, if the pause guard proves unreliable, adds
**$25/month**. Domain and GitHub Pages costs are unchanged.

## 14. Decisions needed from the host

Each item has a recommendation; answering "agree" to all of them is enough to start v0.2.0.

1. **Stack: Supabase + Resend, GitHub Pages unchanged.** Recommend yes. You create both accounts
   under your own email so ownership stays with you; the repo holds the configuration.
2. **Phone sign-in.** Recommend *defer to v0.2.2* and collect phone as an optional contact field. The
   alternative is SMS at launch for about $6–14/month plus one to four weeks of carrier registration
   before the first code can be sent.
3. **Membership gate.** Recommend *gate on*: people you invite or proxy-enter get in automatically;
   anyone else waits for a one-tap approval before seeing the roster. The research notes many small
   groups skip the gate entirely; the roster here includes families and kids counts, which is why the
   recommendation is to keep it.
4. **Public counts.** Recommend *on by default* per trip ("8 people in · 3 vehicles"), with names never
   public. Turn it off per trip if a count feels like pressure.
5. **Messaging scope.** Recommend *announcements plus a group-chat link*, no threads or DMs, per the
   research. Say so if you want replies on the site anyway; it moves to v0.3 otherwise.
6. **Interested state.** Recommend keeping it: followers see the roster and announcements but are not
   counted. Drop it if you would rather keep the states to going / maybe / can't.
7. **Roster display.** First name only, with a last initial only when two first names collide.
   Alternative: always first name + last initial.
8. **Retire `trip.roster` and `peopleTaken` in `guide.json`** in favor of the live roster. Recommend
   yes; the static page keeps a fallback line when the API is down.
9. **Co-hosts.** Per-trip co-hosts are supported in the data model; you name them per trip (no
   assumptions made about who).
10. **Timeline.** v0.2.0 by Oct 31, 2026; v0.2.1 by Dec 15, 2026. Say if Zion's RSVPs need it earlier;
    the foundation can ship without the host dashboard's CSV export and settings screen first.
